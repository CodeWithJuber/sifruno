## Runs that failed first, and why

Evidence is what the server showed; the cause of each is named after it.
No product bug was found. Every failure was in a proof: checks that later
changes to the product made stale (panel-shell, site-domains, the wizard,
the archive mode), one race in a check (broker-web), and two runs that
failed because panel-shell had left its panel running. Each fix is its own
commit, and every rerun passed on the same server.

   - "breadcrumb shows Websites > Static site files (old)": the page reads
     "Static sites (old) > Static site files (old)" since a93102a put it
     under Static sites (old) in the Advanced group.
   - "run completed": at phone width the run opened a browser that was not
     signed in, which since 4fa1858 sees only the sign-in form, so the
     Files heading never came. Once that was fixed, the HTTPS part looked
     for the static site under Websites, which lists WordPress and PHP
     websites since 9432391 (seen in a local run, the same panel and
     browser script).
   - "no page errors": console lines "Failed to load resource: ... 503".
     This proof runs the panel without the account service, and
     Websites (9432391), Files (21eb4dd) and Get started (4bdb95d) read
     /api/v1/websites/sites, /jobs and /backup-storage, which then answer
     503 with the reason. The proof now keeps those 503s apart, checks that
     only those reads answer it and that Websites shows the reason; any
     other console error still fails it.
   Local run of the fixed script against the same build: 51 passed, 0
   failed; then on the server: 51 passed, 0 failed.

## How panel-shell ran on a cloud server

panel-shell was written for the QEMU dev VM, which forwards loopback ports
to the guest's 80 and 443. On this server the run's ports file named two
free local ports as HTTP_PORT and HTTPS_PORT, and one SSH connection
forwarded the first to the panel's loopback port on the server and the
second to the server's 127.0.0.1:443, where the panel's HTTPS listener ran.
The proof's port-80 relay could not bind (OpenLiteSpeed holds port 80) and
was not needed. Requests over the HTTPS forward reach the panel by the
host name panel.sifruno.test, so the panel treats them as remote, as it
would another machine's.

Two proofs cannot share a server in every order: panel-shell needs port
443 free, so it runs before any site has a certificate, and its panel must
be stopped (pkill -x sifruno) before site-domains or migrate-verify. The
other proofs share the server in any order; their accounts have their own
names per run.
